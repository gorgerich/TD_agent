# Тихий дом — Агентская платформа: CJM, логика, копирайт

Документ продуктовой логики кабинета агента. Не визуал (визуал — `DESIGN.md`).
Здесь: путь агента, ветвления, модель жизненного цикла кейса, система статусов,
copy-системы, риски, план. Backbone-сдвиг v3: **кейс описывается операционным
статусом** («что сейчас, что делать»), а не существительным-этапом.

Реализация ядра: `lib/caseStatus.ts` (`deriveCaseStatus`). Статус выводится из
существующих данных (встречи, сметы, заказы, coViewed/coAgreed, документы,
интейк, дата церемонии) — без новых таблиц и миграций.

## 1. CJM агента (сжатая карта)

Контекст: агент работает с семьёй в горе, под жёстким дедлайном (церемония).
Главные эмоции — спешка, ответственность, страх упустить. Интерфейс обязан
снимать неопределённость: всегда видно «что дальше».

| Стадия | Цель агента | Вопрос в голове | Стресс | Что показать | Сбой-стейт |
|---|---|---|---|---|---|
| Открыл платформу | Понять нагрузку дня | «За что хвататься?» | Перегруз | Срочное → сегодня → ждёт клиента/оплату | Стена одинаковых карточек |
| Новый кейс | Быстро завести семью | «Не потерять контакт» | Спешка | Минимум полей: имя, телефон | Длинная форма |
| Вводные | Зафиксировать усопшего, формат, дедлайн | «Что обязательно спросить?» | Память | Интейк: усопший, церемония, бюджет | Не зафиксирована дата церемонии |
| Документы | Собрать обязательное | «Чего не хватает?» | Контроль | Список нужного + кто/к какому сроку | Непонятно, что требуется |
| Смета | Собрать цену под бюджет | «Уложусь ли в бюджет?» | Цена | Конструктор/тариф + бюджет-индикатор | Смета не сходится |
| Логистика | Зал, морг, кладбище, транспорт | «Всё совпадает по времени?» | Координация | Маршрут + время | Конфликт времени |
| Отправка клиенту | Показать смету | «Клиент увидел?» | Ожидание | Статус: отправлена/смотрит/согласовал | Молчание клиента |
| Оплата | Принять аванс/полную | «Сколько ещё должны?» | Деньги | Аванс/остаток/способ | Оплата зависла |
| Ведение | Не упустить задачи/сроки | «Что просрочено?» | Срыв | Просрочки, ближайшие дедлайны | Тихий пропуск дедлайна |
| Завершение | Закрыть, сохранить историю | «Всё закрыто?» | Финал | Чек-лист закрытия | Незакрытый хвост |

## 2. Flow-map (ветвления → состояние экрана)

- **Погребение vs кремация** → набор обязательных документов и услуг разный
  (урна/контейнер vs гроб/могила). CTA конструктора одинаковый, состав разный.
- **Зал нужен / нет** → блок длительности зала появляется только при `hasHall`.
- **Церемония: гражданская / религиозная / комбинированная** → маршрут катафалка
  и доп. услуги (отпевание) появляются по выбору.
- **Документы полны / нет** → статус кейса `Готовим смету и документы`, риск-флаг
  «Нет документов» при стадии Договор/Оплата.
- **Оплата: нет / аванс / полная** → статус `Ожидаем оплату` → `Аванс получен`
  → `Оплачено`. Next action меняется: принять аванс → принять остаток → церемония.
- **Клиент: не смотрел / смотрит / согласовал** → `Смета отправлена` →
  `Клиент смотрит смету` → `Клиент согласовал смету`.
- **Кейс активный / просрочен / завершён** → бейдж-исключение только при
  просрочке/церемонии<48ч/застое (закон «Тишина по умолчанию», DESIGN.md).
- **Встреча есть / нет** → `Новый кейс` (назначить встречу) vs `Встреча назначена`.
- **Срочная задача есть / нет** → блок «Просроченные задачи» в дашборде.
- **Много кейсов / пусто** → список vs обучающий empty state.

## 3. Модель жизненного цикла кейса (операционные статусы)

Источник истины — `deriveCaseStatus()`. `stageIdx` (0..5) питает линейный
степпер; `label`/`next`/`waiting`/`tone` — операционный слой.

| key | label | stageIdx | next (исход) | ждём | условие |
|---|---|---|---|---|---|
| `new` | Новый кейс | 0 | Назначить встречу, заполнить вводные | info | нет встреч |
| `meeting-set` | Встреча назначена | 0 | Провести встречу, собрать вводные | — | встреча в будущем |
| `collecting-info` | Собираем информацию | 1 | Заполнить данные семьи и усопшего | info | встреча, интейк неполон |
| `preparing` | Готовим смету (и документы) | 1 | Собрать смету | docs/— | интейк ок, сметы нет |
| `quote-ready` | Смета готова | 2 | Отправить смету клиенту | — | смета есть, ссылки нет |
| `quote-sent` | Смета отправлена | 2 | Ждём клиента, при паузе напомнить | client | ссылка есть, не открыл |
| `client-viewing` | Клиент смотрит смету | 2 | Связаться, ответить на вопросы | client | открыл, не согласовал |
| `client-agreed` | Клиент согласовал смету | 3 | Оформить договор, принять оплату | — | coAgreed, заказа нет |
| `await-payment` | Ожидаем оплату | 3 | Принять аванс или полную оплату | payment | открытый заказ, не оплачен |
| `deposit` | Аванс получен | 4 | Принять остаток оплаты | payment | PARTIALLY_PAID |
| `paid` | Оплачено | 4 | Согласовать дату церемонии | — | PAID, церемония не назначена |
| `ceremony-scheduled` | Церемония запланирована | 4 | Подготовить логистику | — | PAID + ceremonyAt в будущем |
| `done` | Кейс завершён | 5 | Кейс закрыт, история сохранена | — | COMPLETED |

Срочность (urgent) — отдельный слой поверх статуса: просрочка задачи, церемония
< 48 ч с пробелами, застой > 7 дней. Влияет на сортировку и бейдж, не на label.

## 4. IA / навигация (решения)

Разделы оставлены, роли уточнены (без дублей):
- **Кейсы** — командный центр + список. Главный экран.
- **Календарь** — встречи, церемонии, дедлайны (связан с кейсами).
- **Сметы** — агрегат всех смет по статусу (черновик/отправлена/согласована).
- **Документы** — агрегат: что требуется/загружено/готово, по кейсам.
- **Задачи** — агрегат задач со всех кейсов (сегодня/просрочены/позже/готово).
- **Настройки**, **Обучение** — служебные.

Принцип: списочные разделы (Сметы/Документы/Задачи) — это **срезы** кейсов,
а не отдельные сущности. Любая строка ведёт в кейс.

## 5. Copy-системы

### Tone of voice
Спокойно, по-деловому, уважительно, операционно, кратко. Без игривости,
стартап-жаргона, маркетинга, агрессивной срочности, восклицаний.

### Naming
Кейсы · Календарь · Сметы · Документы · Задачи · Комиссии. («Кейс» прижился как
рабочий термин агента — оставлен; «дело» как синоним в тексте.)

### Кнопки = исход (не «Создать»/«Продолжить»)
- `Новый кейс`, `Создать кейс`
- `Отправить смету клиенту`, `Открыть смету`, `Показать клиенту`
- `Принять оплату`, `Назначить встречу`, `Заполнить вводные`
- `Изменить детали` (раскладка тарифа), `Сохранить план`

### Статусы — операционные (см. таблицу §3)
Запрещены: «Активный», «В работе», «Выполнено». Только «что сейчас».

### Empty states — учат следующему шагу
- Нет кейсов: «Здесь будут ваши кейсы. Создайте первый, чтобы вести клиента от
  первого контакта до оплаты.» + [Создать кейс]
- Нет встреч сегодня: «На сегодня встреч нет. Проверьте активные кейсы без
  следующего шага.»
- Нет просрочек: «Просроченных задач нет. Следующие действия — в активных кейсах.»

### Ошибки — по-человечески + что делать
- Не «Ошибка сохранения данных» → «Не удалось сохранить изменения. Проверьте
  интернет и попробуйте снова.»

### Уведомления — что/почему/что делать
- Не «Документ обновлён» → «Клиент загрузил свидетельство о смерти. Проверьте и
  продолжите оформление.»

## 6. UX-риски и решения

| Риск | Решение |
|---|---|
| Стена одинаковых карточек | Операционный статус + сортировка по срочности |
| Бейдж-шум (всё «без движения») | Бейдж только исключение; демо-данные засеять свежими |
| Агент не знает «что дальше» | `next` в каждом кейсе описывает исход |
| Прыжки между страницами | Деталь кейса с табами; срезы ведут в кейс |
| Технический язык в ошибках | Copy-система ошибок (§5) |
| Дедлайн церемонии тихо проходит | Церемония < 48 ч → красный, перебивает статус |

## 7. Реализовано / план

**Готово (этот проход):**
- `lib/caseStatus.ts` — движок операционных статусов.
- Список кейсов + деталь кейса вшиты на движок (статус-чип, next-исход).
- Copy: убран combat/Postgres-жаргон логина, «Операционка» → «Работа по кейсам».
- DESIGN.md v3 «Quiet Depth» (визуальный слой).

**Следующие проходы (стадированы, без миграций где можно):**
- Дашборд-бакеты: Срочное / Сегодня / Ждёт клиента / Ждёт оплату / В работе.
- Полный copy-проход по формам/плейсхолдерам/валидации/тостам (§5 как чек-лист).
- Документы: «зачем нужен / кто предоставит / к какому сроку» в строке.

**Требует решения владельца (миграции данных):**
- Поле `responsible` у задачи, явный `blocker`-флаг, тип задачи от стадии.
- Явный `caseStatus` в БД (сейчас выводится) — если понадобится фильтрация/отчёты.
