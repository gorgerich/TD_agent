### P2-OBS: Repeated attempts retain an old completed outcome while running

Location: lib/rateLimitRetentionHealth.ts:23-26, with completion update at35-41.

The initial insert sets lastOutcome RUNNING, but its ON CONFLICT branch changes only lastAttemptAt. After one successful observation, a second attempt therefore starts with a new lastAttemptAt while lastOutcome remains SUCCEEDED and lastDeleted/budgetExhausted/lastCompletedAt still describe the first attempt. If the second request stalls or is terminated before finally, the record never entered RUNNING for that attempt; health continues to return the old success outcome with stale=false until the old success ages past26h. Concurrent completions also lack an attempt-generation predicate, so a completion cannot be associated with the latest attempt from the shared row alone.

This does not show unsafe deletion, privilege bypass or a P1 failure. It does weaken the new observed-job status as a detector of an unfinished latest execution. Either explicitly model the returned outcome as the last completed attempt and expose current/incomplete attempt state separately, or persist RUNNING on repeat attempts with generation-aware completion so an older run cannot finish a newer attempt. Add deterministic tests for success -> held second run, termination/no completion, and reversed success/failure completion order. The current five-concurrent-success test checks row uniqueness and freshness, not those status associations.
