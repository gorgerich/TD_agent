## Canonical synthetic smoke account

`scripts/ops/smoke-account.ts` invokes `manageSmokeAccount()` and supports
`provision`, `status`, `disable`, `enable` and `rotate`. Secrets enter only through
environment variables. Password and password hash are never printed or included
in the secret-free audit JSON.

Provisioning creates exactly these records in one serializable transaction:

1. one `User`:
   - fixed synthetic `.invalid` email;
   - fixed synthetic display name;
   - `phone = null`;
   - PBKDF2 password hash generated by existing `lib/password.ts`;
2. one `Agent` linked 1:1 to that user:
   - `status = ACTIVE`;
   - lowest-commission existing `AgentTier` (read only; no tier is created);
   - `selfEmployed = false`;
   - `onboardingCompleted = true`;
   - `notifyEnabled = false`.

No narrower RBAC role exists in Week 1. Minimum available privilege is therefore
an ordinary `ACTIVE` agent confined to its own empty agent tenant. The account is
safe for permanent controlled smoke use because it contains synthetic identity
only, owns no domain data, uses a strong secret-manager credential and supports
rotation/suspension. Suspension blocks new password sessions; existing stateless
cookies expire after the existing eight-hour TTL, so release procedure must also
discard the operator cookie after smoke.

Strong-password policy: at least 32 characters and at least three character
classes. Provision is idempotent: a second run verifies the existing password and
returns `replayed=true`; a mismatched credential fails and requires explicit
`rotate`. Any owned `ClientLead` or `Meeting` blocks provision/enable and rolls
back. Disable, rotation and status remain available so contamination cannot prevent
containment. Audit output exposes the non-zero counts. A `Case` requires a lead
foreign key, so zero owned leads prevents canonical case creation during Week 2 backfill.
